# ResearchTrack SE3112 — Final k6 Performance Testing Evidence

This folder is the final evidence package for the ResearchTrack **Load & Performance Testing** contribution. It is designed to be placed at the repository root (or submitted as a standalone evidence folder) without changing the runtime code.

## 1. What this package proves

The performance suite exercises the deployed ResearchTrack production-like Azure environment from an external persistent VPS using k6. It covers authenticated read traffic, expected load, stress, sudden spikes, bounded writes, the full student/supervisor submission lifecycle, and signed Jira webhook ingestion.

All seven final evidence runs passed their finalized performance and correctness gates. The suite also records detailed endpoint metrics and preserves the raw evidence needed for viva/demo verification.

## 5. Architecture and execution model

The test runner is deliberately outside the Azure application environment. k6 runs on the persistent VPS and sends real HTTPS traffic through the production API Gateway. This avoids measuring only local/container networking and gives a more realistic view of end-to-end latency.

The workflow authenticates with dedicated ResearchTrack supervisor/student test accounts. Normal authentication is used rather than bypassing application authentication. For heavy manual profiles, Gateway rate limiting is temporarily exempted only when both the discovered VPS egress IP and the dedicated performance token match. The workflow captures the pre-test Gateway/Azure runtime state and restores it independently after the test, including threshold-failure cases.

## 6. Profiles

**Smoke** is the lightweight deployment-health and latency profile. It uses two looping VUs for 45 seconds and is suitable for automatic post-deployment execution.

**Load** models expected steady-state concurrent reads with an arrival-rate ramp of 2→4→10 req/s and cooldown.

**Stress** increases demand to 40 req/s to reveal latency degradation and saturation behavior.

**Spike** applies an abrupt 2→40→2 req/s burst to validate sudden demand and recovery behavior.

**Write** runs bounded submission-requirement create/delete operations, one iteration every three seconds for 30 seconds.

**Lifecycle** performs one complete student/supervisor submission lifecycle: create requirement, create upload session, PUT object to storage, complete v1, request changes, upload/complete v2, approve, verify history, and archive the test requirement.

**Webhook** sends signed Jira issue-update webhook traffic at a ramping 1→2→12 req/s arrival rate for 50 seconds.

## 7. Correctness gates

Latency is not considered sufficient evidence by itself. The profiles also gate on business failure rate, correctness checks, and HTTP 429 responses. Final evidence runs recorded 0 business failures, 100% checks, and 0 HTTP 429 responses across all seven profiles.

## 8. Key performance finding

Jira Issues is the principal tail-latency contributor in the read-heavy profiles. In the final runs its p95 ranged from 4.30 s in Smoke to 4.77 s in Spike, while most other read endpoints remained in the few-hundred-millisecond range. This endpoint is therefore preserved as a diagnostic metric rather than given one universal endpoint-specific gate.

This is a useful viva finding: the system remained functionally correct while integration-related tail latency dominated the overall p95 under heavier read workloads.

## 9. CI/CD policy

Automatic post-deployment **Smoke** is the continuous performance gate because it is short and low impact. Load, Stress, Spike, Write, Lifecycle, and Webhook remain controlled manual profiles for evidence, regression investigation, or planned performance validation. Heavy destructive/side-effecting profiles should not be scheduled blindly against the production-like environment.

## 10. Evidence traceability

Every JSON summary records the workflow name, GitHub run ID, run attempt, source SHA, execution mode, target base URL, project ID, threshold source, and pass/fail result. The original downloaded GitHub artifact ZIPs are retained unchanged under `evidence/source-artifacts/`, while extracted contents live under `evidence/final-runs/`.

## 11. How to use this package during the viva

Start with this README and `docs/03-FINAL-RESULTS.md`. Then open one standalone HTML report, ideally Stress or Spike, to demonstrate percentile latency, throughput, Jira Issues tail behavior, 0% failures, 100% checks, and 0 HTTP 429. Open Lifecycle to demonstrate the real cross-service/storage business journey and Webhook to demonstrate signed asynchronous integration load.

Use `docs/05-VIVA-GUIDE.md` for a concise explanation of architecture choices, thresholds, findings, and likely examiner questions.

## 12. Security

This evidence folder intentionally contains no passwords, access keys, client secrets, SSH private keys, performance bypass token, or signed S3 URLs. Configuration documentation uses variable names only. Secrets must remain in GitHub Actions/Environment secrets and the deployed platform's secret store.

## 13. Final conclusion

The final evidence demonstrates a repeatable, authenticated, externally executed k6 performance-testing pipeline with runtime-configured quality gates, endpoint diagnostics, controlled Gateway handling, restoration guarantees, automatic post-deployment Smoke capability, detailed machine/human-readable reports, and workload coverage from routine traffic through stress, spike, write, lifecycle, and webhook scenarios.

All seven final manual evidence profiles passed their finalized gates.
